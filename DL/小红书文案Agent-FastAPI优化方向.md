# 小红书爆款文案 Agent —— 融合 FastAPI 的优化方向

> 背景：项目原本基于 Dify 实现小红书爆款文案生成 Agent，现计划引入 FastAPI 后端技术进行产品化升级。
>
> 核心思路：**从"低代码单点工具"升级为"可扩展的产品化服务"**，让 Dify 和 FastAPI 各司其职，而不是用 FastAPI 重写 Dify 已经做好的部分。

---

## 一、先想清楚：Dify 与 FastAPI 的职责边界

这是最关键的一步。合理分层能避免重复造轮子。

| 层 | 职责 | 谁来负责 |
|---|---|---|
| **LLM 编排层** | Prompt 管理、多轮对话、工具调用、RAG 检索 | Dify（已调好的部分继续用） |
| **业务服务层** | 用户体系、鉴权、配额、内容持久化、业务规则 | FastAPI |
| **数据层** | 用户 / 文案 / 模板 / 历史记录 | FastAPI + DB |
| **接入层** | Web、小程序、开放 API | 前端调用 FastAPI |

### 推荐架构

```
前端（Web / 小程序）
        │
        ▼
FastAPI（统一网关 + 业务服务）
        │
        ▼
Dify API（LLM 编排）
        │
        ▼
LLM（大模型）
```

> FastAPI 作为统一入口，屏蔽 Dify 的实现细节，对外提供干净的 API。

## 二、核心优化方向

### 1. 接入方式：FastAPI 代理 Dify

- 通过 Dify 的 `/v1/chat-messages` 或 `/v1/workflows/run` 接口调用
- 用 FastAPI 做 **流式转发（SSE）**，前端实时看到文案逐字生成
- **收益**：API Key 不下发到前端，可统一做鉴权 / 限流 / 日志

### 2. 用户与商业化能力（Dify 弱项）

- JWT 鉴权、用户注册登录
- **配额与计费**：免费次数、会员、按次扣费（Redis 计数）
- 生成历史记录持久化（PostgreSQL / MySQL）

### 3. 内容质量与业务增强（真正的差异化）

- **爆款模板库**：把优质 prompt 结构化成模板，支持分类（美妆 / 穿搭 / 探店…）
- **RAG 知识库**：接入平台热词、爆款标题库、行业话术，让 Dify 检索后生成
- **多方案生成 + 打分**：一次生成 N 个版本，用规则 / 模型打分排序
- **多平台适配**：同一主题输出小红书 / 抖音 / 公众号不同风格

### 4. 性能与稳定性

- **Redis 缓存**：相同输入直接返回，避免重复消耗 token
- **异步任务队列（Celery / RQ）**：长文案生成转后台任务，前端轮询 / 推送
- **限流熔断**：防止刷接口，保护 LLM 额度
- **可观测性**：请求日志、token 消耗统计、生成成功率监控

## 三、推荐落地路线（分阶段）

### 阶段一｜最小闭环
- FastAPI 封装一个 `/generate` 接口，内部调 Dify，支持流式返回
- 加 JWT 鉴权 + 简单的调用日志

### 阶段二｜产品化
- 接入数据库存历史记录
- 加用户体系 + Redis 配额管理
- 模板库管理接口（增删改查）

### 阶段三｜增强
- RAG 知识库（热词 / 爆款库）
- 多版本生成 + 打分排序
- 异步队列 + 缓存 + 限流
- 监控面板

### 阶段四｜平台化
- 对外开放 API（给第三方调用）
- 多平台风格适配
- A/B 测试不同 prompt 的转化率

---

## 四、技术选型建议

```
Web 框架:    FastAPI + Uvicorn
ORM:         SQLAlchemy 2.0 (async) / SQLModel
数据库:      PostgreSQL（可加 MySQL）
缓存/队列:   Redis + Celery
鉴权:        JWT (python-jose) + passlib
流式:        sse-starlette
部署:        Docker Compose（FastAPI + Dify + PG + Redis）
```

---

## 五、关键提醒

1. **先想清楚要不要保留 Dify**。如果业务逻辑越来越重，长期可考虑把 prompt 迁移到 FastAPI + LangChain，Dify 只留做可视化调试；但初期**保留 Dify 作为编排层**最省事。
2. **流式体验**是文案类产品刚需，别做成"转圈等 10 秒"。
3. **缓存和配额**直接决定成本，务必早做。
4. **模板库 + RAG** 才是区别于"随便调个 API"的核心壁垒。
